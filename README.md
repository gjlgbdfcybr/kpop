# ВышКат

Консольное приложение для учёта транспорта и вещей сервиса проката. Домашнее задание №1 по конструированию программного обеспечения: ООП, SOLID, DI-контейнер и юнит-тесты.

Реализация на C++17, используются только стандартные библиотеки. Интерфейс программы и сообщения об ошибках — на английском.

## Сборка и запуск

Нужен компилятор с поддержкой C++17. Для команд ниже используется `g++`, доступный в `PATH`. На Windows подходит MinGW-w64. Дополнительные библиотеки, CMake и Python для сборки и запуска не нужны.

Откройте терминал в папке с `main.cpp`, `model.cpp`, `model.hpp` и `tests.cpp`.

Приложение, Windows PowerShell:

```powershell
g++ -std=c++17 -Wall -Wextra main.cpp model.cpp -o app.exe
.\app.exe
```

Тесты:

```powershell
g++ -std=c++17 -Wall -Wextra tests.cpp model.cpp -o tests.exe
.\tests.exe
```

На Linux/macOS с установленным g++:

```sh
g++ -std=c++17 -Wall -Wextra main.cpp model.cpp -o app
./app
g++ -std=c++17 -Wall -Wextra tests.cpp model.cpp -o tests
./tests
```

Приложение и тесты собираются отдельно: в `main.cpp` и `tests.cpp` находятся разные функции `main`. Файл `model.cpp` нужен обеим программам, а `model.hpp` подключается через `#include` и отдельно не компилируется. Перед повторной сборкой закройте запущенный исполняемый файл.

## Возможности

- Приём самокатов и велосипедов после техосмотра.
- Учёт шлемов и зарядных станций.
- Проверка уникальности инвентарных номеров среди всего имущества.
- Отчёт о количестве транспорта, количестве вещей и суммарной суточной энергии.
- Список принятого транспорта для новичков: простота управления не ниже 6.
- Общий список номеров и названий транспорта и вещей.

Меню:

| Пункт | Действие |
|---|---|
| `1. Show report` | Количество транспорта и вещей, общее число объектов, расход энергии в кВт·ч/сутки |
| `2. Show beginner vehicles` | Номера, названия и простота транспорта для новичков |
| `3. Show inventory` | Номера и названия всего имущества |
| `4. Add vehicle` | Добавление самоката или велосипеда |
| `5. Add equipment` | Добавление шлема или зарядной станции |
| `0. Exit` | Выход |

При добавлении транспорта вводятся вид, номер, название, простота и исправность тормозов (`1` — исправны, `0` — неисправны). Для самоката дополнительно вводится расход энергии. Для вещи вводятся вид, номер и название; для зарядной станции — также расход энергии.

Названия могут содержать пробелы. Дробная часть числа вводится через точку. Некорректное число запрашивается повторно. Числа вне допустимого диапазона, включая вид объекта, простоту и состояние тормозов, запрашиваются повторно без потери ранее введённых полей. Ошибка текстовых данных завершает попытку добавления и возвращает в меню. Конец ввода завершает программу.

## Правила и допущения

- Номер и название не могут быть пустыми. Пробелы автоматически не удаляются, регистр номера учитывается: `S-001` и `s-001` — разные номера. Отдельная проверка строк из одних пробелов не реализована.
- Простота — целое число от 1 до 10 включительно.
- Расход энергии — конечное неотрицательное число. Ноль допустим; отрицательные значения, бесконечность и NaN запрещены.
- `ServiceCenter` использует упрощённый техосмотр: проверяет исправность тормозов. Состояние вводит оператор. Неисправный объект можно создать, но такой транспорт не принимается в парк обычным сервисом.
- Перед техосмотром проверяется уникальность номера. `Park::get_last_error()` возвращает причину последнего отказа при добавлении: занятый номер, отказ техосмотра или отсутствие объекта. Новая попытка добавления очищает старую ошибку. Отклонённый транспорт не учитывается в отчётах и не резервирует номер.
- Вещи не проходят проверку тормозов и не попадают в список транспорта для новичков.
- Энергия суммируется по всем объектам, реализующим `EnergyConsumer`: сейчас это самокаты и зарядные станции. Велосипеды и шлемы не потребляют электричество. Введённые расходы считаются самостоятельными величинами без двойного учёта зарядки.
- Данные хранятся только в памяти. При каждом запуске создаётся один и тот же примерный парк. Сохранение на диск и удаление объектов не реализованы и заданием не требуются.

## Демонстрация работы

При запуске уже добавлены:

| Номер | Объект | Простота | Энергия, кВт·ч/сутки |
|---|---|---:|---:|
| S-001 | City scooter | 7 | 2.5 |
| B-001 | City bike | 5 | Не потребляет |
| H-001 | City helmet | Не применяется | Не потребляет |
| C-001 | Charging station | Не применяется | 3.0 |

Сразу после запуска пункт `1` показывает 2 транспорта, 2 вещи и `5.5 kWh/day`. Пункт `2` показывает только `S-001`, пункт `3` — все четыре объекта.

Последовательно можно показать следующие сценарии:

| Действие | Ожидаемый результат |
|---|---|
| Добавить через пункт `4` велосипед B-002, название New bike, простоту 6 и исправные тормоза | `Added`; транспорта становится 3, велосипед появляется в списке новичков, энергия остаётся 5.5 |
| Добавить транспорт с новым номером B-003 и неисправными тормозами | `Rejected`; состав парка не изменяется |
| Добавить шлем с номером S-001 | Отказ из-за номера, уже занятого транспортом |
| Добавить через пункт `5` шлем H-002 | `Added`; вещей становится 3 |
| Добавить зарядную станцию C-002 с расходом 1.5 | `Added`; вещей становится 4, суммарная энергия — 7 |
| Указать простоту 11 или отрицательную энергию | Повторный запрос того же поля; ранее введённые данные сохраняются |
| Указать пустой номер | Сообщение об ошибке; объект не добавляется |
| Вместо числа ввести `abc`, затем корректное число | Повторный запрос без завершения программы |
| Ввести неизвестный пункт меню, например 99 | Повторный запрос команды из диапазона 0–5 |
| Выбрать 0 | Программа завершается |

Пустой парк и подмена техосмотра дополнительно проверяются автоматическими тестами. В обычном меню парк изначально заполнен примерами.

## Структура проекта и модель

| Файл | Назначение |
|---|---|
| [model.hpp](model.hpp) | Объявления интерфейсов и классов |
| [model.cpp](model.cpp) | Реализация правил, учёта и контейнера |
| [main.cpp](main.cpp) | Ввод, меню, вывод результатов и первоначальное заполнение парка |
| [tests.cpp](tests.cpp) | Юнит-тесты и их запуск |

Иерархия инвентарных объектов:

```text
Inventoriable — интерфейс номера и названия
└── InventoryItem — хранение и проверка общих данных
    ├── Vehicle — простота и состояние тормозов
    │   ├── Bicycle
    │   └── Scooter — дополнительно реализует EnergyConsumer
    └── Equipment
        ├── Helmet
        └── ChargingStation — дополнительно реализует EnergyConsumer
```

`EnergyConsumer` выделен отдельно, чтобы шлем и обычный велосипед не получали ненужный метод расхода энергии. `InspectionService` описывает техосмотр, `ServiceCenter` реализует обычную проверку. `Park` отвечает за приёмку, уникальность номеров и отчёты.

Транспорт и вещи находятся в отдельных коллекциях `unique_ptr`. Это позволяет хранить наследников без срезки объектов и автоматически освобождать память. `get_inventory()` объединяет их для чтения через `Inventoriable`. Указатели из отчётов не владеют объектами: их нельзя удалять, и они действительны только пока существует соответствующий парк.

`get_total_energy()` проверяет наличие интерфейса `EnergyConsumer` через `dynamic_cast`. Проверяется способность потреблять энергию, а не конкретное имя класса.

## DI-контейнер

`Park` получает ссылку на `InspectionService` через конструктор. Он не создаёт `ServiceCenter` и не выбирает реализацию техосмотра самостоятельно.

`Container` — небольшой специализированный DI-контейнер: хранит ссылку на выбранный сервис и создаёт парк через `create_park()`, передавая ему эту зависимость. Универсальная регистрация типов и внешняя библиотека DI не нужны для одного сервиса.

```cpp
ServiceCenter service;
Container container(service);
auto park = container.create_park();
```

Каждый вызов `create_park()` создаёт новый парк со своей коллекцией имущества. Сервис не принадлежит контейнеру или парку: он должен существовать дольше объектов, которые ссылаются на него. В `main` это обеспечивается порядком объявления переменных.

## SOLID и обязательные вопросы

### Какие принципы применены

- **SRP:** классы модели проверяют свои данные; `ServiceCenter` решает вопрос допуска; `Park` ведёт баланс; функции в `main.cpp` отвечают за ввод и вывод. Логика парка не зависит от консоли.
- **OCP:** новые наследники `Vehicle` и `Equipment` могут использовать существующую приёмку и отчёты. Новый потребитель энергии реализует `EnergyConsumer`, после чего участвует в суммировании без изменения `Park`.
- **LSP:** самокат и велосипед используются через `Vehicle`, шлем и станция — через `Equipment`. Наследники соблюдают общие ограничения данных. Для безопасного удаления через базовые указатели предусмотрены виртуальные деструкторы.
- **ISP:** `Inventoriable`, `EnergyConsumer` и `InspectionService` задают отдельные небольшие контракты. Объекты не обязаны реализовывать не относящиеся к ним операции.
- **DIP:** `Park` зависит от абстракции `InspectionService`; конкретный сервис передаётся через контейнер.

### Какой принцип наиболее явно выражен

**DIP** в связке `InspectionService` → `Park` → `Container` из [model.hpp](model.hpp) и [model.cpp](model.cpp). Реализацию техосмотра можно заменить, не меняя код парка. Это проверяется тестом `test_service_replacement_through_container`.

### Какой принцип сознательно ограничен

**OCP** в консольных функциях `add_vehicle_from_input` и `add_equipment_from_input` из [main.cpp](main.cpp): новый доступный пользователю вид потребует нового варианта выбора и ветви создания. Для небольшого фиксированного меню это проще реестра фабрик и плагинов. Сам учёт в `Park` при этом не меняется.

### Что произойдёт при расширении

- **Новый вид транспорта:** наследуется от `Vehicle`, а при потреблении электричества реализует `EnergyConsumer`. Общие приёмка, подсчёт и отбор новичков продолжают работать. Нужно добавить пункт создания в меню; при новых критериях осмотра — расширить или заменить реализацию `InspectionService`.
- **Новая вещь:** наследуется от `Equipment`, при необходимости реализует `EnergyConsumer`. Приёмка и общий список имущества работают без отдельного вектора для нового типа.
- **Сотрудник:** не должен наследовать `Inventoriable` или попадать в `Park`, поскольку сотрудники не ставятся на баланс. Потребуется отдельная модель и учёт сотрудников.
- **Склад запчастей:** для количественных остатков, поступлений и списаний потребуется отдельный складской сервис. Текущий парк учитывает индивидуальные объекты по уникальным номерам, а не партии расходных материалов.

### Какие тесты фиксируют техосмотр и правило для новичков

В [tests.cpp](tests.cpp):

- `test_inspection` проверяет приём исправного транспорта, отказ неисправному, отсутствие его в отчётах и возможность повторно использовать номер после отказа.
- `test_beginner_boundary` проверяет, что простота 5 не подходит, а 6 и 10 подходят; вещи не включаются в список транспорта.
- `test_service_replacement_through_container` подставляет `RejectingService`, всегда возвращающий отказ, и тестовый `AcceptingService`, всегда возвращающий согласие. Сервис передаётся конструктору `Container`, затем парк создаётся через `create_park()`. Так проверяется, что парк следует решению внедрённого сервиса.

## Тестирование

Девять тестовых функций проверяют пустой парк, техосмотр, дубликаты номеров, границу простоты, энергию и общий баланс, подмену сервиса через контейнер, неверные данные и передачу `nullptr` вместо объекта и причины отказа.

Использован небольшой запускатель без внешних зависимостей. `check` бросает исключение при невыполненном условии; `run_test` сообщает `PASS` или `FAIL` и продолжает остальные проверки. В отличие от `assert`, эти проверки не отключаются при сборке с `NDEBUG`. При успешном запуске выводится `9/9 tests passed`, код завершения — 0; при ошибке — 1.
